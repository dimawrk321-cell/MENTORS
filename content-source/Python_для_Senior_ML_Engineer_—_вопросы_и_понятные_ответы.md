# Python для Senior ML Engineer — вопросы и понятные ответы

## 1. Типы данных и объекты

### 1. Какие типы данных в Python изменяемые, а какие неизменяемые?

Изменяемый объект можно поменять после создания, не создавая вместо него новый объект. К таким типам относятся списки, словари, множества и большинство объектов пользовательских классов.

Неизменяемые объекты после создания изменить нельзя. Это числа, строки, кортежи, `frozenset`, `None`.

Главный практический момент в том, что один изменяемый объект может использоваться сразу в нескольких местах программы. Если его изменить через одну переменную, изменение будет видно и через другие переменные, которые указывают на этот же объект.

Важно также понимать, что неизменяемость контейнера не означает неизменяемость всего его содержимого. Например, кортеж нельзя изменить как кортеж, но если внутри него находится список, сам список менять можно.

---

### 2. В чем разница между `==` и `is`?

`==` сравнивает значения объектов: одинаковое ли у них содержимое.

`is` проверяет, являются ли две переменные ссылками именно на один и тот же объект.

Например, можно создать два разных списка с одинаковыми элементами. Для них `==` даст истину, а `is` — ложь.

На практике `is` чаще всего используют при сравнении с `None`, потому что `None` существует в одном экземпляре.

---

### 3. Что такое ссылки в Python?

В Python переменная фактически хранит не сам объект, а ссылку на него.

Поэтому если две переменные получили один и тот же список, то фактически у нас не два списка, а две ссылки на один объект.

Это особенно важно при работе с изменяемыми объектами: изменение через одну ссылку будет видно через другую.

Понимание ссылок помогает разобраться в копировании объектов, передаче аргументов в функции и неожиданных изменениях данных.

---

# 2. Списки и кортежи

### 4. В чем разница между списками и кортежами?

Главное различие — список изменяемый, а кортеж неизменяемый.

Список стоит использовать, когда набор элементов может меняться: что-то добавляется, удаляется или заменяется.

Кортеж лучше использовать для фиксированной структуры данных, которая после создания меняться не должна.

Кортеж обычно занимает немного меньше памяти, потому что Python не нужно предусматривать возможность его расширения.

Кроме того, кортеж можно использовать ключом словаря, если все его элементы тоже могут быть ключами.

---

### 5. Как работает список под капотом? Какова сложность `len()`?

Список в Python устроен как динамический массив ссылок на объекты.

Python хранит отдельно текущую длину списка и объём выделенной под него памяти.

Поэтому получение длины через `len()` выполняется за O(1): Python не пересчитывает элементы, а просто возвращает уже сохранённое число.

Получение элемента по индексу тоже O(1).

Добавление элемента в конец обычно O(1). Иногда памяти становится недостаточно, тогда Python выделяет новый, более крупный участок памяти и переносит туда ссылки — конкретное добавление в этот момент может занять O(n).

Добавление элемента в начало или середину обычно O(n), потому что часть элементов необходимо сдвинуть.

---

### 6. Что использовать вместо списка при очень большом количестве данных, например 10 млрд элементов?

В первую очередь я бы не пытался загрузить такой объём в обычный Python-список.

Если это числовые данные, обычно эффективнее использовать NumPy, потому что значения там хранятся компактно и без большого объёма служебной информации Python.

Если данные не помещаются в оперативную память, можно читать их частями, использовать файлы с отображением в память, базы данных или инструменты для распределённой обработки.

Для ML основная идея здесь такая: большие данные лучше обрабатывать батчами или потоково, а не пытаться целиком разместить в оперативной памяти.

То есть на таком объёме задача уже не столько в выборе структуры данных, сколько в правильной организации самого процесса обработки.

---

### 7. Что больше весит: список или кортеж?

При одинаковых элементах список обычно занимает больше памяти.

Причина в том, что список может увеличиваться. Чтобы при каждом добавлении элемента не выделять память заново, Python заранее оставляет небольшой запас.

У кортежа размер фиксирован при создании, поэтому дополнительный резерв ему не нужен.

При этом важно понимать: сами объекты внутри списка или кортежа обычно не копируются — контейнеры хранят ссылки на них.

---

# 3. Словари

### 8. Что вы знаете о словарях в Python?

Словарь хранит пары «ключ — значение» и внутри реализован через хеш-таблицу.

Поиск, добавление и удаление элемента в среднем выполняются за O(1).

Это достигается за счёт того, что для ключа вычисляется специальное числовое значение — хеш, по которому Python быстро определяет, где искать нужный элемент.

Ключ должен быть хешируемым, то есть его хеш не должен неожиданно меняться во время использования в словаре.

Современные словари Python также сохраняют порядок добавления элементов.

---

### 9. Почему поиск в словаре обычно O(1)?

При поиске Python не перебирает все ключи подряд.

Сначала вычисляется хеш ключа, после чего Python практически сразу понимает, в какой области таблицы находится элемент.

Поэтому количество элементов в словаре обычно почти не влияет на время поиска.

O(1) — это средняя сложность. Если возникает много коллизий, отдельные операции могут быть дороже.

---

### 10. Какие объекты могут быть ключами словаря?

Ключ должен быть хешируемым.

Чаще всего это числа, строки, `None`, `frozenset` и кортежи из хешируемых объектов.

Списки, словари и множества ключами быть не могут, потому что их содержимое можно изменить.

Основная идея: пока объект используется как ключ, его положение в хеш-таблице должно оставаться предсказуемым.

---

### 11. Что такое коллизии в хеш-таблицах?

Коллизия возникает, когда разные ключи приводят Python к одной и той же позиции или области хеш-таблицы.

Это нормальная ситуация — полностью избежать коллизий невозможно.

В таком случае Python дополнительно ищет подходящую свободную позицию и при поиске проверяет не только хеш, но и равенство самого ключа.

Если таблица становится слишком заполненной, Python увеличивает её размер. Это помогает сохранять быстрый поиск.

---

### 12. Может ли кортеж быть ключом словаря?

Да, если все элементы внутри кортежа хешируемы.

Кортеж из чисел и строк использовать можно.

Если внутри кортежа находится список, использовать такой кортеж в качестве ключа уже нельзя, потому что список изменяемый и не является хешируемым.

---

# 4. Копирование объектов

### 13. В чем разница между `copy()` и `deepcopy()`?

Обычная поверхностная копия создаёт новый внешний объект, но вложенные объекты остаются общими.

Например, если скопировать список, внутри которого находятся другие списки, внешний список будет новым, а вложенные списки останутся теми же объектами.

Глубокое копирование пытается рекурсивно создать независимые копии всех вложенных объектов.

Но `deepcopy` гораздо дороже по памяти и времени. В реальных проектах его не стоит использовать автоматически — сначала нужно понять, действительно ли нужна полностью независимая копия всей структуры.

---

### 14. Почему опасно использовать изменяемый объект как значение по умолчанию функции?

Потому что значение по умолчанию создаётся один раз при определении функции, а не заново при каждом вызове.

Если в качестве значения по умолчанию поставить список и потом что-то в него добавлять, следующие вызовы функции увидят уже изменённый список.

Это одна из классических ошибок Python.

Обычно вместо списка или словаря используют `None`, а новый объект создают уже внутри функции.

---

### 15. Можно ли сделать изменяемый класс хешируемым?

Технически можно, но делать это нужно очень осторожно.

Если хеш объекта зависит от его полей, а потом эти поля изменить, словарь или множество могут перестать корректно находить объект.

Поэтому хорошее правило: данные, которые участвуют в сравнении и вычислении хеша объекта, не должны меняться, пока объект используется как ключ.

На практике объекты-ключи обычно делают неизменяемыми.

---

# 5. ООП

### 16. Что такое `self`?

`self` — это ссылка на конкретный экземпляр класса.

Через `self` метод понимает, с каким именно объектом сейчас работает, и получает доступ к его полям и другим методам.

Например, если создано десять объектов одного класса, `self` позволяет одному и тому же методу работать с состоянием конкретного объекта.

Само название `self` не является обязательным для языка, но это стандартное соглашение Python.

---

### 17. Что такое инкапсуляция?

Инкапсуляция — это идея о том, что внутреннее устройство объекта лучше скрывать за понятным интерфейсом.

Пользователь класса должен понимать, что объект умеет делать, но ему не обязательно знать, как именно это реализовано внутри.

В Python строгих приватных полей практически нет.

Один символ `_` означает: «это внутренняя часть объекта, напрямую лучше не использовать».

Два `_` запускают механизм изменения имени атрибута, но это скорее защита от случайного обращения или конфликта имён, а не полноценная безопасность.

На практике хорошая инкапсуляция уменьшает связанность кода и позволяет менять внутреннюю реализацию без переписывания всего проекта.

---

### 18. Что такое наследование?

Наследование позволяет создать новый класс на основе существующего и переиспользовать его поведение.

Дочерний класс может использовать методы родительского класса или переопределять их.

При этом на практике наследование стоит применять аккуратно. Если классы связаны только потому, что хочется переиспользовать код, часто лучше собрать объект из нескольких компонентов, чем строить сложную цепочку наследования.

Глубокие иерархии классов обычно сложнее поддерживать.

---

### 19. Что такое полиморфизм?

Полиморфизм позволяет работать с разными объектами через одинаковый интерфейс.

Например, у нас могут быть совершенно разные модели машинного обучения, но если у каждой есть понятный метод получения предсказания, остальной код может работать с ними одинаково.

В Python это особенно естественно: обычно важнее не конкретный класс объекта, а наличие у него нужного поведения.

Для больших проектов такие интерфейсы можно дополнительно описывать через типизацию.

---

### 20. Что такое магические методы и какие вы знаете?

Магические методы — специальные методы Python с двойным подчёркиванием в начале и конце имени.

Python сам вызывает их при определённых действиях.

Например:

- `__init__` — инициализация объекта;
- `__str__` — понятное строковое представление;
- `__repr__` — техническое представление объекта;
- `__len__` — работа с `len`;
- `__getitem__` — получение элемента по индексу;
- `__iter__` и `__next__` — перебор элементов;
- `__enter__` и `__exit__` — работа с `with`;
- `__call__` — возможность использовать объект как функцию;
- `__eq__` — сравнение через `==`;
- `__hash__` — вычисление хеша.

Их смысл в том, что пользовательский класс можно сделать похожим по поведению на встроенные объекты Python.

# 6. Генераторы

### 21. Что такое генераторы и зачем они нужны?

Генератор позволяет получать значения постепенно, по мере необходимости, а не создавать всю последовательность заранее.

Например, если нужно обработать миллион строк файла, необязательно загружать миллион строк в память. Можно читать по одной строке или небольшими частями.

Генератор хранит только текущее состояние вычисления и умеет продолжить работу с того места, где остановился.

В ML это удобно для обработки больших наборов данных, чтения файлов, подготовки батчей и потоковой обработки.

---

### 22. Как можно создавать генераторы?

Основной вариант — функция с `yield`.

`yield` возвращает очередное значение, но не завершает функцию окончательно. При следующем обращении выполнение продолжается с того же места.

Для простых случаев есть генераторные выражения.

Также можно вручную создать объект, который поддерживает последовательный перебор элементов через специальные методы, но это используется реже и обычно нужно, когда требуется более сложное управление состоянием.

---

### 23. Можно ли использовать `yield` и `return` в одной функции?

Да.

`yield` выдаёт значение и временно приостанавливает функцию.

`return` окончательно завершает генератор.

Поэтому `return` можно использовать, например, когда нужно досрочно остановить выдачу элементов.

---

# 7. Декораторы

### 24. Что такое декораторы?

Декоратор позволяет добавить функции дополнительное поведение, не переписывая саму функцию.

Например, одна и та же логика может использоваться для:

- логирования;
- измерения времени выполнения;
- проверки доступа;
- кеширования;
- повторной попытки при ошибке;
- сбора метрик.

Это удобно, когда одна техническая логика должна применяться к большому количеству функций.

---

### 25. Какие декораторы используются на практике?

Из стандартных часто используются:

- `property`;
- `classmethod`;
- `staticmethod`;
- `lru_cache`;
- `dataclass`.

В рабочих проектах часто пишут свои декораторы для измерения времени, логирования, повторных попыток и сбора метрик.

Для ML это может быть, например, замер времени инференса или логирование вызовов модели.

---

# 8. Контекстные менеджеры

### 26. Что такое контекстный менеджер?

Контекстный менеджер позволяет выполнить подготовительные действия перед блоком кода и гарантированно выполнить завершающие действия после него.

Самый известный пример — работа с файлом через `with`.

Даже если внутри блока возникнет ошибка, файл будет корректно закрыт.

Этот механизм полезен для файлов, соединений с БД, блокировок, временного изменения режима работы библиотеки и других ресурсов.

---

### 27. Какие примеры контекстных менеджеров знаете?

Типичные примеры:

- открытие файла;
- соединение с базой данных;
- блокировка при работе с потоками;
- `torch.no_grad()` при работе с PyTorch;
- временное подавление конкретного исключения;
- пользовательский контекстный менеджер.

В ML хороший пример — отключение вычисления градиентов при предсказании модели, потому что для инференса градиенты не нужны и только расходуют память.

---

### 28. Почему файл лучше открывать через `with`?

Потому что файл будет закрыт автоматически независимо от того, чем закончится выполнение блока.

Без `with` разработчик должен сам следить за закрытием файла, в том числе при возникновении ошибки.

Если этого не делать, можно получить утечки файловых дескрипторов и проблемы при длительной работе сервиса.

---

### 29. Что будет, если внутри `with` возникнет ошибка?

Контекстный менеджер всё равно выполнит завершающую часть.

Например, файл будет закрыт, соединение освобождено, блокировка снята.

После этого исключение обычно продолжит распространяться дальше.

При необходимости контекстный менеджер может самостоятельно обработать исключение и не передавать его дальше.

---

# 9. Исключения

### 30. Что такое исключения и как с ними работать?

Исключения — механизм обработки ошибок и нестандартных ситуаций.

Основные конструкции:

- `try` — код, в котором может возникнуть ошибка;
- `except` — обработка конкретной ошибки;
- `else` — выполняется, если ошибки не было;
- `finally` — выполняется в любом случае;
- `raise` — позволяет явно вызвать исключение.

Хорошая практика — перехватывать конкретные типы ошибок.

Если просто ловить все ошибки и ничего с ними не делать, можно скрыть настоящую проблему и сильно усложнить поиск ошибок.

---

### 31. Какие ключевые слова Python вы знаете?

Я бы не перечислял их подряд, а разделил по назначению.

Есть слова для условий и циклов: `if`, `else`, `for`, `while`.

Для функций: `def`, `return`, `yield`, `lambda`.

Для обработки ошибок: `try`, `except`, `finally`, `raise`.

Для асинхронной работы: `async`, `await`.

Для импорта: `import`, `from`, `as`.

Для работы с областью видимости: `global`, `nonlocal`.

Есть также `with`, `class`, `in`, `is`, `and`, `or`, `not`.

Важно понимать, что, например, `self` — это не ключевое слово Python, а принятое имя параметра.

# 10. Память

### 32. Как Python выделяет память?

Большинство Python-объектов размещается в области динамической памяти, которой управляет сам интерпретатор.

Когда создаётся объект, Python выделяет память не только под его данные, но и под служебную информацию: тип объекта, количество ссылок на него и другие данные.

Python дополнительно оптимизирует работу с большим количеством небольших объектов, чтобы постоянно не обращаться напрямую к операционной системе.

В ML важно понимать, что память Python, память NumPy и память видеокарты — не одно и то же. Они могут управляться разными механизмами.

---

### 33. Как Python освобождает память?

В CPython основной механизм — подсчёт ссылок.

Python знает, сколько ссылок существует на объект.

Когда ссылок становится ноль, объект больше нельзя использовать, и память можно освободить.

Проблема возникает, когда два объекта ссылаются друг на друга. Формально ссылки на них остаются, хотя программе они уже не доступны.

Для таких случаев существует дополнительный сборщик мусора.

---

### 34. Как работает Garbage Collector?

Основную часть объектов CPython удаляет через подсчёт ссылок.

Garbage Collector нужен в первую очередь для поиска циклических ссылок.

Например, объект A ссылается на B, а B — обратно на A. Даже если больше программа эти объекты не использует, их счётчики ссылок не равны нулю.

Сборщик мусора периодически анализирует такие группы объектов и удаляет те, до которых программа больше не может добраться.

Для ML важно помнить: удаление Python-объекта не обязательно означает мгновенное физическое освобождение памяти видеокарты. Например, PyTorch отдельно управляет GPU-памятью и может оставлять освобождённые блоки у себя для повторного использования.

---

# 11. GIL

### 35. Что такое GIL?

GIL — механизм CPython, который в обычной конфигурации не позволяет нескольким потокам одновременно исполнять Python-код внутри одного процесса.

Это упрощает внутреннюю работу интерпретатора и управление объектами.

Поэтому если у нас тяжёлые вычисления написаны именно на Python, добавление потоков обычно не позволит использовать несколько ядер процессора одновременно.

Но это ограничение относится именно к выполнению Python-кода. NumPy, PyTorch и другие библиотеки часто выполняют тяжёлые вычисления внутри C/C++ или на GPU и могут работать параллельно.

---

### 36. Чем плох GIL и как его обходить?

Основной недостаток проявляется в тяжёлых вычислениях на CPU: несколько Python-потоков не дадут нормального параллельного ускорения.

Основные варианты:

- использовать несколько процессов;
- переносить вычисления в NumPy, PyTorch и другие библиотеки, где тяжёлая работа выполняется не самим Python;
- использовать GPU;
- распределять вычисления между несколькими процессами или машинами.

Для ML последний вариант особенно типичен: основная математика обычно всё равно выполняется не Python-интерпретатором.

---

# 12. Асинхронность, потоки и процессы

### 37. Что такое асинхронность?

Асинхронность позволяет программе не простаивать, пока она ждёт завершения медленной операции.

Например, сервис отправил запрос во внешний API. Вместо того чтобы просто ждать ответа, он может в это время обрабатывать другие запросы.

В Python для этого используются `async`, `await` и цикл, который управляет задачами.

Асинхронность хорошо подходит для большого количества сетевых запросов, работы с сервисами и другими задачами, где значительная часть времени уходит именно на ожидание.

Для тяжёлых вычислений сама по себе она ускорения не даёт.

---

### 38. Что такое многопоточность?

Внутри одного процесса можно создать несколько потоков.

Они используют общую память, поэтому могут легко работать с одними и теми же объектами.

Это удобно, но появляется риск одновременного изменения общих данных, поэтому иногда нужны блокировки.

В Python потоки хорошо подходят для задач, где много ожидания: запросы к сети, базе данных, чтение файлов.

Для тяжёлых вычислений на чистом Python эффективность ограничивает GIL.

---

### 39. Что такое многопроцессорность?

При многопроцессной работе запускается несколько отдельных процессов Python.

У каждого процесса собственная память и собственный интерпретатор.

Поэтому они действительно могут выполнять вычисления одновременно на разных ядрах процессора.

Недостаток — процессы тяжелее потоков и между ними сложнее передавать данные.

Для ML процессы часто используются при подготовке данных, параллельном чтении датасета и других CPU-нагруженных операциях.

---

### 40. Когда использовать асинхронность, потоки или процессы?

Сначала нужно понять, на чём программа теряет время.

Если большая часть времени — ожидание большого количества сетевых запросов, хорошо подходит асинхронность.

Если используется библиотека, которая работает синхронно, но тоже в основном ждёт сеть, файлы или БД, можно использовать потоки.

Если задача действительно нагружает CPU Python-вычислениями, лучше использовать процессы.

В ML есть ещё важный случай: если вычисления уже выполняются в NumPy, PyTorch или на GPU, сначала нужно посмотреть, как сама библиотека использует ядра и устройства. Дополнительные процессы не всегда ускоряют работу и иногда даже создают лишние расходы.

---

### 41. Как ограничить число одновременных запросов к API, например максимум до пяти?

Для этого удобно использовать семафор.

Его смысл очень простой: одновременно разрешается выполнять только заданное количество операций.

Если разрешено пять запросов и пять уже выполняются, шестой ждёт, пока один из первых пяти завершится.

При этом в реальном сервисе одного ограничения числа одновременных запросов обычно недостаточно.

Стоит также учитывать таймауты, повторные попытки, временные ошибки сервиса и ответы о превышении лимита.

Отдельно нужно различать ограничение «не более пяти запросов одновременно» и, например, «не более ста запросов в минуту». Это две разные задачи.

---

### 42. Как память разделяется между потоками и процессами?

Потоки одного процесса используют общую память.

Поэтому один поток может работать с объектами, которые создал другой поток. Это удобно для передачи данных, но создаёт риск конфликтов при одновременном изменении данных.

При этом у каждого потока есть собственный стек вызовов.

У процессов память изолирована. Один процесс напрямую не видит объекты другого процесса.

Чтобы обмениваться данными, нужны специальные механизмы передачи данных или общая память.

Для ML это особенно важно при больших массивах: если бездумно копировать огромный датасет между процессами, можно быстро закончить всю оперативную память.

---

### 43. В чем разница между потоками и процессами?

Потоки легче создавать и они используют общую память.

Из-за этого между ними проще передавать данные, но сложнее безопасно менять общее состояние.

Процессы тяжелее, память у них независимая, но они позволяют действительно параллельно выполнять Python-вычисления на разных ядрах.

Если совсем коротко:

**потоки — легче и удобнее для ожидания; процессы — тяжелее, но лучше подходят для независимых CPU-вычислений.**

---

### 44. Какие задачи подходят потокам, а какие процессам?

Потоки хорошо подходят для:

- запросов по сети;
- работы с БД;
- чтения и записи файлов;
- вызова внешних сервисов.

Процессы подходят для:

- тяжёлой обработки данных на CPU;
- преобразования изображений;
- вычислений, написанных преимущественно на Python;
- независимой параллельной обработки частей данных.

В ML типичный пример процессов — несколько workers, которые параллельно готовят данные для обучения модели.

---

### 45. Почему потоки обычно используют для I/O-задач?

Потому что при ожидании ответа от сети, БД или файла поток фактически не выполняет Python-код.

В это время интерпретатор может переключиться на другой поток и продолжить полезную работу.

Если же все потоки постоянно выполняют тяжёлые Python-вычисления, они начинают конкурировать за GIL и нормального параллельного ускорения обычно не получается.

Но важно не говорить, что потоки вообще никогда не помогают вычислениям: некоторые библиотеки выполняют работу вне Python и могут использовать несколько потоков эффективно.

---

### 46. Приходилось ли работать с `asyncio`?

Хороший ответ:

Да, использовал для задач с большим количеством операций ожидания — например, когда нужно параллельно обращаться к нескольким API или внешним сервисам.

Основная идея понятная: пока один запрос ждёт ответ, программа занимается другими запросами.

При этом обязательно контролирую число одновременно выполняемых операций, ставлю таймауты и корректно обрабатываю ошибки, чтобы внешний сервис не перегружался и один зависший запрос не останавливал весь процесс.

---

### 47. В чем преимущество `asyncio` перед потоками?

При большом количестве одновременно ожидающих сетевых операций асинхронный подход обычно требует меньше памяти и ресурсов.

Переключение между задачами происходит только в понятных местах, где программа ожидает результат.

Это удобно, например, если сервис одновременно обслуживает сотни или тысячи запросов.

Но асинхронность не всегда лучше потоков. Если проект небольшой или используемые библиотеки не поддерживают асинхронную работу, потоки могут быть проще и достаточно эффективны.

---

# 13. Принципы разработки

### 48. Что такое SOLID?

SOLID — набор принципов, которые помогают делать код проще для развития и поддержки.

**Single Responsibility** — компонент должен отвечать за одну понятную задачу.

**Open/Closed** — желательно иметь возможность добавлять новое поведение без постоянного переписывания уже работающего кода.

**Liskov Substitution** — дочерний класс должен действительно уметь заменить родительский без неожиданного изменения поведения.

**Interface Segregation** — лучше несколько небольших понятных интерфейсов, чем один огромный.

**Dependency Inversion** — основная бизнес-логика не должна жёстко зависеть от конкретной технической реализации.

Для ML хороший пример последнего принципа: код обучения модели не должен быть намертво связан с конкретным местом хранения данных. Если данные сегодня лежат локально, а завтра в S3, хотелось бы поменять только слой работы с хранилищем.

---

### 49. Что означает DRY?

DRY означает, что одно и то же правило или знание не стоит поддерживать одновременно в нескольких местах.

Например, если преобразование признаков отдельно написано для обучения модели и отдельно для продакшена, со временем эти реализации могут разойтись.

В результате модель обучалась на данных, обработанных одним способом, а в продакшене получает данные, обработанные иначе.

Поэтому общую логику лучше переиспользовать.

Но и чрезмерно обобщать код не стоит. Иногда две похожие функции проще и понятнее, чем одна огромная универсальная конструкция.

---

# 14. Типизация

### 50. Что такое типизация в Python?

Python использует динамическую типизацию.

Тип относится к самому объекту, а переменная может в разное время ссылаться на объекты разных типов.

При этом в Python можно указывать подсказки типов для аргументов функций, возвращаемых значений и переменных.

Python сам по себе обычно не запрещает передать другой тип во время выполнения, но специальные инструменты могут заранее проверить код и найти часть ошибок.

В большом ML-проекте типизация особенно полезна на границах компонентов: например, можно явно указать, что функция принимает таблицу определённого вида и возвращает массив предсказаний.

Это уменьшает количество ошибок и делает код понятнее для команды.

---

# 15. Контейнеризация и архитектура

### 51. Зачем нужна контейнеризация?

Контейнер позволяет собрать приложение вместе с необходимыми зависимостями и запускать его в одинаковой среде на разных машинах.

Это решает классическую проблему: «у меня локально работает, а на сервере нет».

Для ML контейнеры особенно полезны, потому что часто есть чувствительные зависимости: версия Python, PyTorch, CUDA, системные библиотеки.

Если всё это зафиксировано в контейнере, окружение можно воспроизводить.

Контейнеры также удобно использовать для развёртывания нескольких экземпляров сервиса, например если нужно увеличить количество серверов с моделью при росте нагрузки.

---

### 52. Как микросервисы могут взаимодействовать друг с другом?

Самый простой вариант — один сервис напрямую отправляет запрос другому и ждёт ответ.

Например, сервис приложения отправляет признаки в сервис модели и ждёт предсказание.

Это удобно, когда результат нужен сразу.

Другой подход — отправить сообщение в очередь. Тогда отправитель не обязан ждать немедленного ответа. Получатель обработает сообщение, когда сможет.

Такой вариант удобен для фоновых задач, логирования, обработки больших потоков событий.

Есть также gRPC — более компактный и быстрый способ взаимодействия сервисов со строгим описанием формата сообщений. Его часто используют для внутреннего общения сервисов.

Выбирать подход нужно по задаче.

Если пользователю прямо сейчас нужен ответ модели — обычно удобнее прямой запрос.

Если нужно сохранить информацию о предсказании, посчитать статистику или позже запустить переобучение — это уже можно делать через очередь.

На senior-уровне важно не просто перечислить технологии, а понимать, что выбор зависит от скорости ответа, нагрузки, надёжности и того, должен ли отправитель ждать результат.
